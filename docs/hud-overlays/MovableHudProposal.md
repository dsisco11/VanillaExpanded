# Movable HUD indicators

## Recommendation

Reuse Vintage Story's HUD/dialog lifecycle, GUI event routing, native bounds and scaling, and native dialog-position persistence. Prefer the stock titlebar's drag behavior where it can be adapted to hover controls; extend the existing VE layout runtime for individual placement and player-created groups formed by snapping. Individual feature overlays and their presentation classes should not implement dragging or persistence.

This proposal describes the complete intended interaction. The shared runtime provides effective default/independent/custom containers, persisted permissions and origins, mixed pair-tree layout, individual detachment, and snap-based creation, insertion, and merging. In-game interaction acceptance remains separate from source and headless validation.

Implementation checklist: [MovableHud.todo](MovableHud.todo).

## Base-game findings

The investigation used the local API source and the installed Vintage Story 1.22.7 client assembly.

| Facility | Verified behavior | Reuse |
| --- | --- | --- |
| `HudElement` / `GuiDialog` | HUDs are native dialogs. `HudElement` does not request an ungrabbed mouse. Mouse delivery and input capture are separately overridable. | Keep the existing native HUD host; enable narrowly scoped pointer interaction. |
| `GuiComposer` / `GuiElement` | Composers dispatch mouse down, move, and up to interactive elements. Bounds support hit testing and native parent/child geometry. | Implement the handle as a native GUI element, using the existing compositions. |
| `GuiElementDialogTitleBar` | Its Fixed/Movable menu enables dragging. Mouse movement updates parent `fixedX/Y` using pixel delta divided by GUI scale. Release stores the position. | Prefer native dragging, with an adapter for hover visibility and snapping. |
| `IGuiAPI.GetDialogPosition` / `SetDialogPosition` | Installed `GuiAPI` delegates directly to global `ClientSettings`. | Reuse native origin access and mirrors under the authoritative layout snapshot, with stable VE namespaced keys. |
| `GetDialogBoundsInArea` | Installed implementation returns open composer bounds whose `Alignment` equals the requested dialog area. | Bounds discovery only; this is not a snapping or docking service. |
| `GuiDialog.GetFreePos` / `OccupyPos` / `FreePos` | Reserves predefined flag-based window positions. | Not appropriate for arbitrary player placement or edge alignment. |

No general snapping or docking facility was found in the inspected native GUI API and window-drag path. Stock dragging changes positions freely; it does not calculate neighboring edges or snap relationships.

The stock titlebar already supplies the essential dragging and persistence. Its direct use of native client settings is suitable. It is not a complete drop-in solution for the proposed hover-only handles: its movable/moving state and setup methods are private, it includes close/menu controls, and it exposes no public drag-completed callback. Prefer a narrow adapter around native event handling and parent bounds, with snapping applied before release stores the position. Hover rendering, small indicator dimensions, and cancellation need validation before claiming that the widget can be reused unchanged. Retain native titlebar and dropdown machinery through the compact skin; native coordinate storage remains reusable; membership requires additional metadata.

Native `GuiManager` dispatches mouse events through registered dialogs until one handles them. A handled mouse-down also invokes its focus-management path, which can unfocus another dialog even if the HUD itself is non-focusable. Interaction must respect foreground windows and must be checked with inventories and other dialogs open; setting `Focusable = false` alone does not guarantee that other dialog focus remains untouched.

Source references: [titlebar](../../../vsapi/Client/UI/Elements/Impl/Interactive/GuiElementDialogTitleBar.cs), [HUD base](../../../vsapi/Client/UI/HudElement.cs), [dialog input](../../../vsapi/Client/UI/Dialog/GuiDialog.cs), [composer](../../../vsapi/Client/UI/GuiComposer.cs), [bounds](../../../vsapi/Client/UI/ElementBounds.cs), [GUI API](../../../vsapi/Client/API/IGuiAPI.cs). Installed `GuiManager` and `GuiAPI` implementations were also inspected to verify dispatch and storage behavior.

## Player interaction

- Show handles only while the mouse is ungrabbed, the HUD is visible, and no foreground dialog owns that pointer location. Normal gameplay keeps the existing passive behavior.
- Hovering an indicator reveals its container's titlebar. Individual members have no titlebar: drag their visible content to move them individually, or use the container titlebar to move the group. A singleton container retains its container menu for permission and reset access.
- Handles are transient overlays. They do not enlarge measured indicator footprints, shift neighboring indicators, or trigger content preparation. Place them above the target when space permits and below it at the screen edge. Keep the handle visible while the pointer travels from the indicator to it, and throughout dragging.
- Left-drag a grip to move its target, or drag a visible indicator itself to move that individual. A body drag detaches the member of a multi-member group; the group grip still moves the complete group. Native titlebar/menu interactions take priority. Content dragging uses drawable clipped bounds, requires Movable permission and a free cursor, and respects foreground windows. Empty group space is not a drag target. Consume pointer events only for an eligible body/grip interaction or active drag; leave clicks elsewhere unchanged. Continue the drag outside the original bounds until release.
- A group drag moves its currently grouped members together and preserves their packing. Dragging an individual indicator away detaches it from automatic packing and gives it its own placement. Remaining members close the gap.
- Dropping an individual onto a grouping snap creates a group with an independent target, or adds the item to the target group. Dragging an individual away removes it from that group. Group controls move the current members together. Dragging an individual away is the ungroup operation. Provide one global Reset HUD layout action that restores all indicators to their built-in groups and positions; no per-indicator or per-group reset is required. Custom groups need stable internal IDs, not predefined names.
- Escape or right-click cancels an active drag and restores its starting placement. Mouse capture changes, world exit, GUI hiding, target removal, or loss of the active interaction cancel safely rather than saving a partial drag.
- Unlocked mouse movement editing exposes every registered indicator. Normal drawable presentations remain unchanged; hidden, disabled, inapplicable, empty, or failed items use compact outlined initials with full hidden-item identity on hover, so they can be moved without fabricated readings or feature activation. Locking the mouse restores normal visibility. The global HUD must remain enabled/visible and the player session ready. Unregistered saved integrations have no item to preview.

### Hover control composition

Use the existing hover targeting to find a drawable indicator under a free cursor. Its visible body and the containing container's titlebar are distinct targets, with an explicit target identity for each interaction. Individual member controls never render, compose, or accept input through their own titlebar.

Place the controls in a separate native control composition so their visibility never changes the measured content footprint or group packing. The control composition follows the target's effective bounds. Keep it visible while the pointer moves from the indicator onto the controls and throughout an active drag; hide it when neither region is hovered and no interaction remains active.

Prototype a narrow adapter around `GuiElementDialogTitleBar` that forwards native mouse events, gates rendering and hit testing to the hover/drag state, uses a stable dialog name for persistence, and observes the resulting parent bounds for layout updates and snapping. The control composition's origin and the persisted content origin must use a consistent mapping, including when the titlebar appears below an indicator near a screen edge.

The adapter uses `GuiElementDialogTitleBar` with its actual native Fixed/Movable dropdown. Its titlebar skin is compact: 22 GUI units high with normal HUD caption text and the radial menu's orange hover background. Only container/group bars have captions; individual member bars remain absent. The native menu/close controls and drag area remain available. Native menu and close glyphs and their hit rectangles follow the slimmer geometry. Retain the native dropdown interaction rather than a direct mode-toggle button. Keep the proven cancellable content-drag integration around the widget so cancellation does not commit a position.

The group control implementation composes the native titlebar with this compact skin and uses its own `GuiElementListMenu`, including native menu selection callbacks. A small adapter isolates access to the titlebar's private menu/icon bounds and suppresses its first-render parent-position write: the temporary hover titlebar position is not the saved content position. Content dragging and cancellation remain owned by the shared movement integration rather than the titlebar's private drag state. Native initialization, menu resources, and dropdown behavior are reused without patching the engine. Native source/headless contract checks and user acceptance remain separate evidence requirements.

Show a partly transparent orange panel behind the exact group bounds while hovered or interacting. While the cursor is free and the group is Movable, also show an unfilled orange line rectangle around those bounds, including when the pointer is elsewhere. Use the radial menu's orange palette for both. Keep these decorations outside measurements and placement calculations. Foreground windows suppress hover fill and controls at their pointer locations, but the movable outline remains a global free-cursor cue. Hide it for hidden HUDs, a grabbed cursor, unavailable content, or modal input capture.

## Placement and group behavior

Groups are runtime containers formed by player actions, rather than fixed named destinations. Any registered indicator can join another indicator's group. Stable feature identities retain sampling, visibility, and resource ownership; built-in group definitions supply initial/reset arrangements only. Custom groups use opaque stable IDs and need no user-assigned name.

Resolve membership and placement before packing, without rewriting feature registrations or duplicating overlays. Layout and scheduler availability consume the same effective container. Independent and user-positioned containers use screen availability even when their former native anchor disappears. Preserve native scaling, integer content origins, and effective screen clamping.

Individual dragging previews removal from the source group, closing its gap. A successful grouping drop creates or joins a target group; a free drop leaves the item independent. Cancellation restores starting membership, order, identity, and placement without writes. Free group dragging preserves membership; a successful grouping snap may merge the entire group into the destination. Hidden/inapplicable members retain saved membership and attachments. In unlocked-mouse editing, prepared stand-ins provide visible targets without touching feature state. Outside editing, their layout space collapses when normal visibility transitions release their footprint; visible members close the gap. When they return, their space reopens using the saved arrangement. Visibility changes do not remove members or normalize their groups into different persistent containers.

Each item belongs to exactly one container. Remove empty groups; normalize singleton groups into independent items without moving their displayed content when free; docked singletons retain the external attachment and source padding. Preserve metadata for temporarily unavailable indicator IDs. Repack after visibility/size/style changes while retaining the free container origin or docked external pivot, subject to reachability. Size changes preserve attachment sides, alignments, and gaps; connected neighbors reposition as needed rather than retaining obsolete offsets. Keep the free group top-left origin fixed; docked containers preserve their external pivot, subject to screen clamping.

### Approved interaction decisions

- Adjacent-edge snapping to an independent item creates a group; snapping to a grouped item inserts into its existing group. Do not create nested groups.
- Highlight the destination, insertion side/order, and resulting layout before release. Only the selected grouping candidate changes membership.
- Screen-edge and matching-edge/center guides remain alignment aids. Shift bypasses snapping and grouping, permitting independent nearby placement.
- Whole-group merging is approved. Snapping a dragged group to another group or an independent indicator combines them, preserving both existing internal arrangements. Show the combined arrangement before release. Commit a single flat membership set, with no duplicate items or nested player-facing groups. Shift bypasses grouping; Escape restores both original arrangements without writes.
- Fixed groups accept individual joins and whole-group merges. Fixed prevents dragging the target group itself; joining does not enable its movement. For free destinations, grow toward the incoming item while preserving the opposite outer edge, subject to screen clamping. Docked destinations retain their external pivot. Left/top insertion may move the saved outer origin outward without moving permission to Movable.
- Fixed/Movable controls dragging permission only and preserves placement and membership when toggled. Global Reset HUD layout restores built-in groups and positions; it is the only restore-default action. Adapt the native Fixed callback so it cannot reset placement or erase custom membership.

Mixed two-dimensional arrangements are approved. Do not restrict a group to one row or column. Support attachment on all four sides: above, below, left, and right. Left/right attachments offer top, center, and bottom alignment; above/below attachments offer left, center, and right alignment. Select alignment by pointer position and show the resulting arrangement in the preview. Overlapping grouping snaps are rejected rather than automatically rearranging existing items. Fixed locks both group dragging and individual detachment; incoming joins/merges remain allowed. The detailed representation below is approved. Resize propagation that preserves attachments, alignment, and spacing with a fixed free-group top-left origin or docked external pivot (subject to screen clamping) is approved. Hidden-member space collapsing with retained membership and attachments is approved. Fixed-target joins and merges are approved. A single global Reset HUD layout action is approved; no partial reset actions are required.

### Native layout reuse assessment

The inspected local API supports the geometry foundation but not a complete user docking model:

- `ElementBounds.ParentBounds`/`ChildBounds`, `WithChild`, alignment, padding, fixed/percentage sizing, and GUI scaling provide native hierarchy and geometry. `GuiComposer.BeginChildElements` attaches bounds through that hierarchy.
- `ElementBounds.RightOf` retains a `LeftOfBounds` reference. Fixed horizontal calculation reads that sibling's calculated X and outer width. This is a limited live horizontal dependency, not a four-direction constraint solver; reference calculation order and invalidation remain caller responsibilities.
- `BelowCopy`, `FixedUnder`, `FixedRightOf`, and `FixedLeftOf` copy or assign coordinates when called. They do not retain a relationship that automatically follows later reference-size changes.
- `FitToChildren` measures child extents; it does not choose an arrangement or close gaps from hidden children. Its extent calculation uses maximum right/bottom extents, so negative child positions require normalization. Percentage-sized axes are excluded from the corresponding fit calculation; avoid circular parent-fit/child-percentage sizing.
- `GuiComposer` owns composition, elements, input dispatch, and rendering. `OnlyDynamic` supports existing HUD dispatch; `ReCompose` rebuilds composition resources and should not be the mechanism for each drag update.

Approved: use native `GuiComposer` and `ElementBounds` systems as the rendering and geometry foundation. Add a focused VE attachment resolver for the chosen mixed arrangement: membership, relative attachment descriptions, dependency ordering, cycle/conflict handling, hidden-member policy, and normalization into a container-local nonnegative coordinate space. Apply resolved GUI-unit rectangles to native bounds, then reuse native scaling, root movement, clipping, and existing feature draw dispatch. Internal layout relationships need not become nested player-facing groups.

Do not serialize `ElementBounds` or composers as layout metadata, or infer persistence from native hierarchy. Persist stable IDs and chosen attachment descriptions separately. The four attachment sides, three alignments per side, and internal pair-tree representation below are approved. Runtime implementation remains separate from this design contract.

Source: [ElementBounds](../../../vsapi/Client/UI/ElementBounds.cs), especially `CalcWorldBounds`, `buildBoundsFromChildren`, `RightOf`, and the fixed/copy helpers; [GuiComposer](../../../vsapi/Client/UI/GuiComposer.cs), especially child scopes, `Compose`, `ReCompose`, and `OnlyDynamic`. Vanilla `GuiDialogTrader` also uses `RightOf` and fixed positioning helpers for authored layouts.

## Snapping and membership commits

Separate geometric candidate calculation from grouping changes. Geometry returns adjusted bounds, guides, and candidate identity; a grouping resolver determines create/join versus alignment-only behavior.

- Use a 16-physical-pixel acquisition threshold and a 26-pixel release threshold, independent of GUI scale. Valid nearby grouping candidates outrank alignment-only guides, including retained screen guides. Within each intent, retain a valid grouping target/member/side (or an alignment identity) first, then rank by distance and ordinal candidate identity. Target/side retention survives a change in cross-axis alignment. Finite target-edge distance includes perpendicular separation beyond its endpoints, so distant corners cannot acquire a grouping target.
- Derive unsnapped bounds from starting geometry and total pointer displacement; never accumulate snapped corrections.
- Consider nearby visible item/group measured bounds and screen edges. Exclude the moving container and descendants, hidden content, handles, shadows, and tooltips; reject distant perpendicular spans.
- Treat currently visible fixed vanilla HUDs as read-only alignment boundaries: hotbar composer, health/hunger meter elements, and enabled temporal gear native hover bounds. Sample current physical bounds while dragging; reject missing/invalid/dirty/ambiguous/closed/disabled HUDs and spectator rendering. Exclude ordinary windows and conditional oxygen/boss meters. Native surfaces support matching-edge/center and exterior-edge guides, never grouping or VE ownership; successful screen/native alignment persists a container attachment. Exterior native snaps round away from the surface so native integer checkpoints cannot overlap a fractional sliver. Native boundaries participate in overlap rejection for moving content, source reflow, and expanded destination geometry; Shift permits intentional overlap.
- Use normal packing gaps for adjacency. Preview the destination arrangement without saving membership or recreating feature artwork.
- Cross-axis alignment uses target thirds with a hysteresis margin of the smaller of 6 physical pixels or one twelfth of the target span. Keep the acquired alignment until the pointer moves beyond its expanded zone; deliberate movement can select any of the three alignments without releasing the target/side.
- Screen-edge guides and player-positioned containers use the actual viewport edges without the default anchored-HUD inset; registered defaults retain their configured padding. Reconcile clamping and nearest-integer GUI origins before release. Alignment-only candidates may shift by up to one GUI unit for rounding and boundary clamping; move their guide to the actual resolved position rather than rejecting a fractional alignment. Reject larger shifts or invalid/colliding layouts. Guides and committed geometry must agree.
- Commit membership and placement together only on successful release. All cancellation paths discard the entire preview, including changes to the source group.

Grouped members subsequently move together; alignment-only snaps never create membership; screen/native snaps retain external attachment metadata. Avoid nested groups and arbitrary inter-group attachment graphs.

## Persistence

Continue using native `GetDialogPosition`/`SetDialogPosition` for integer GUI-unit origins. X/Y pairs cannot encode arbitrary membership, order, layout policy, or custom group identities. Position presence alone no longer records detachment.

Store versioned membership/layout metadata in the native string setting specified below. The authoritative snapshot includes origin checkpoints; native position entries are repaired mirrors. No separate VE layout file is required, and metadata is not disguised as coordinate keys.

Define authority and recoverable commit ordering across metadata and native origins before writing either. Two independent stores are not atomic: interrupted or failed drops must reconcile without orphaned members or half-applied layouts. Never persist previews or write on pointer movement.

Retain client-wide layouts across worlds. Define migration from existing native group positions into the initial arrangement and precedence for subsequent explicit membership. Global Reset HUD layout clears all VE layout overrides, including overrides retained for temporarily unavailable integrations, so those indicators also use defaults when they return. Preserve unrelated dialog settings. Ordinary loading, migration, and configuration changes preserve unavailable integration metadata. Validate versions, duplicate membership, invalid references, unknown IDs, and offscreen geometry. Keep saved origins through configuration changes, applying effective clamping without continuous preference writes.

## Approved detailed layout contract

The interaction, representation, and persistence rules in this section are approved. They define the contract for the subsequent runtime implementation tasks.

### Mixed arrangement representation

Use one flat container membership set and an internal ordered binary layout tree. A leaf names one registered indicator. A pair node stores horizontal/vertical orientation, first/second children, start/center/end cross-axis alignment, and the normal layout gap. Container padding remains separate; default template conversion preserves its existing packing padding. These are layout descriptions, not nested movable groups. Each leaf occurs once; repeated references, cycles, and inconsistent membership are invalid.

An individual drop onto an indicator replaces the target leaf with a pair of that leaf and the incoming leaf. Side determines orientation/order; pointer position determines alignment. Other tree relationships remain unchanged. A whole-group merge onto the destination container combines its complete tree with the incoming complete tree, preserving both internal trees. Whole-group targeting uses container bounds rather than a member leaf; preview clearly identifies that destination. An existing destination group keeps its identity and permission; its free outer origin adjusts toward the incoming item to preserve the opposite edge and cross-axis alignment anchor, while a docked destination retains its external pivot; the source container retires only after commit. When the destination is independent, create a fresh opaque group identity while retaining the target permission and applying the same free outward-growth or docked-pivot placement, whether the incoming side is one item or a whole group. Individual insertion into an existing group keeps that group identity.

Compute pair size bottom-up, then place children top-down in nonnegative local GUI units. Horizontal pairs sum widths plus gap and take maximum height; vertical pairs sum heights plus gap and take maximum width. Cross-axis alignment determines child offsets. Use native bounds/composers for resolved geometry, scaling, clipping, and dispatch; do not run native recomposition on each drag update. This supports mixed arrangements while deliberately avoiding arbitrary cyclic edge constraints or overlapping freeform placements inside a group.

A visible grouping preview must be non-overlapping. Reject an invalid snap rather than move existing items to make room. Size changes recompute the same tree, preserving its relationships and the group top-left origin subject to clamping. Insertion and merging instead grow toward the incoming item: left additions preserve the old right edge; right additions preserve the left edge; above additions preserve the bottom edge; below additions preserve the top edge. Cross-axis expansion preserves the selected start, center, or end anchor. This prevents the whole destination from being pushed away merely because its outer origin was held fixed. Native integer rounding and screen clamping remain applicable, and preview and commit use the same adjusted origin, including for Fixed targets. Internal attachment relationships and ordinary size/visibility reflow remain unchanged.

Outside movement editing, a hidden or unavailable leaf contributes no footprint after its normal exit transition releases that footprint. During editing, registered hidden members contribute their prepared placeholder footprints instead. These host-owned labels prepare on the heartbeat, never in drawing/layout; no feature sample or presentation is fabricated. A missing default native anchor uses transient screen placement during editing, with no preference write until an explicit movement/permission action. Mouse capture, global GUI hiding/disabling, and session exit remove edit targets immediately; placeholder resources are released on heartbeat or teardown. A pair with one drawable child uses that child alone, with no gap; a pair with none contributes nothing. Persisted trees and membership are never pruned for visibility. Reappearance restores the original tree. Thus hidden intermediates/branches collapse without inventing temporary attachment references. Outside movement editing, an all-hidden container retains its identity/origin but has no handles or snap targets; prepared edit proxies make registered members visible and targetable while the cursor is free.

Explicit individual detachment removes its leaf and collapses its now-empty structural branch in the committed tree. Its independent screen origin starts at its displayed origin. Preserve the free source container origin while reflowing remaining members; docked remainders retain their external attachment and padding. A true singleton container becomes independent, preserving permission and either its free displayed origin or the source external attachment and padding; actual zero-member containers retire. Count all saved members, including unavailable ones, for normalization. Registration removal alone marks a saved member unavailable, not permanently deleted. Cancelling restores the original trees, identities, membership, permissions, and origins.

### Movement permission and selection

Permission belongs to the effective container and is stored explicitly. Fixed locks group movement and member detachment; its mode menu remains usable to unlock it. Incoming joins/merges remain allowed. Individual body targets and container titlebars remain distinct interaction identities but consult the same container permission. A detached item inherits its source permission; a destination container keeps its permission on insertion/merge. Two independent items forming a group use the targeted item's permission.

Default templates start Fixed. Legacy saved group origins migrate as Movable, matching their existing behavior. Mode changes preserve the current displayed content origin and membership; changing an anchored default container's mode captures that origin as a screen placement so it cannot jump on the toggle. Global reset removes those overrides and recreates Fixed defaults. Permission is not inferred from position presence after migration.

Adjacent grouping candidates use the four approved sides and three alignments each. Matching-edge/center and screen candidates align without joining. Shift bypasses both snapping and grouping. Candidate preview includes side/alignment, destination, resulting trees, source gap closure, and final clamped/rounded geometry; only valid highlighted candidates commit. Colliding grouping and alignment-only candidates are rejected against visible indicator footprints. Free drops that overlap visible indicators cancel without saving; Shift explicitly permits overlap. Never interpret ordinary free placement overlap as a grouping request.

### Metadata storage and recovery

The public [ISettings API](../../../vsapi/Client/API/ISettings.cs) offers bool/int/float/string/string-list keys, not an object setting or multi-key transaction. Native gameplay UI uses string settings for client state (for example `GuiDialogHandbook` stores its category code). The public [mod configuration API](../../../vsapi/Common/API/ICoreAPI.cs) also supports typed JSON load/store. Neither inspected API promises atomic writes spanning a layout and several native position entries.

Use one versioned JSON snapshot in `api.Settings.String["vanillaexpanded:hud:layout"]`, using the supported native string setting rather than a separate file. This requires a small serializer for our data, not serialization of native bounds/composers. The snapshot contains schema version, revision, initialized/reset state, containers, explicit permissions, membership trees and alignments/gaps, and optional integer GUI-unit origin checkpoints. Anchored defaults without overrides retain their default template reference. Snapshot validation occurs before use or replacement.

The snapshot is authoritative for a committed layout and its origin checkpoints; `GetDialogPosition`/`SetDialogPosition` remain the native origin access/mirror boundary. This approved authority model makes membership and positions recoverable together. Missing snapshot means first-time legacy import; a valid empty initialized snapshot means reset defaults and must not re-import stale native positions.

Use stable native keys: retain `vanillaexpanded:hud:group:<registered-group-id>` for default templates, use `vanillaexpanded:hud:custom:<opaque-id>` for custom groups, and `vanillaexpanded:hud:indicator:<indicator-id>` for independent items. Track owned retired/imported keys in the snapshot until cleanup succeeds, including unavailable integrations. Never enumerate or clear unrelated dialog settings.

Successful drop/mode/reset commit: prepare and validate an immutable full candidate, serialize it, then replace the single snapshot setting before touching position mirrors. Publish the new committed in-memory state and synchronize the corresponding native origins; retire source keys only after the new snapshot is accepted. A snapshot-set failure leaves the old state and mirrors intact and cancels the preview. If the API throws after a possible assignment, read the exact stored snapshot back before deciding old versus new state; do not guess. If readback fails, suspend interaction/persistence until the last committed state can be recovered. Mirror failures do not roll back an accepted snapshot: retain pending mirror cleanup and retry at a safe boundary/startup. Loading a valid snapshot always repairs native mirrors from its checkpoints, never the reverse. A default/no-origin record overrides stale native positions; clear or ignore that mirror before constructing controls. Newly available default containers follow the same rule. No preview writes and no preference writes for effective viewport clamping.

This is logical recovery within the engine's settings lifecycle, not a promise of crash-proof disk flushing. A process crash may leave the prior or latest engine-persisted valid snapshot; reconstruction must never combine one snapshot's membership with another's coordinates. Verify actual native string-setting round trips in the later persistence tests/live acceptance; do not infer disk atomicity from the public API.

First import uses registered default membership/packing and legacy group origins; legacy position presence supplies initial Movable mode only during import. Convert built-in ordered horizontal/vertical packing into equivalent pair trees, retaining gap, padding, and cross alignment. Preserve default anchor behavior until a screen override is committed. Explicit snapshot state always takes precedence over legacy keys and unrelated configuration changes. Unknown integration IDs and their saved trees survive ordinary loads and later become drawable when registered. Registered indicators absent from explicit saved membership use their registered default template, filtered to exclude all explicitly assigned IDs. Never insert a newly discovered indicator into a saved custom tree automatically. These implicit default containers retain registered packing/anchors; if an explicit container already owns the default identity/key, use a deterministic default-remainder identity and `vanillaexpanded:hud:default-remainder:<registered-group-id>` key. Do not move existing user containers to make room. Each registered indicator therefore resolves exactly once, including after new integration registration.

Validate supported schema, unique container/indicator IDs, enum values, finite nonnegative gaps/padding, bounded acyclic trees, consistent leaf membership, integer checkpoints, and correct key ownership. Do not silently discard unknown-but-well-formed integration IDs. Malformed/unsupported snapshots remain untouched with a bounded diagnostic; display registered defaults read-only until explicit global reset replaces the invalid snapshot. Do not silently overwrite a newer schema. Global reset writes a valid initialized empty snapshot with the owned-key cleanup inventory before clearing mirrors, preventing stale overrides from reappearing even if cleanup is interrupted. If the old snapshot is malformed or newer, do not trust its keys or require successful parsing to reset: inventory only keys provably owned through current registrations and validated session state. Unknown stale mirrors remain ignored by initialized reset state and are cleared/ignored when their integrations later register; never scan or erase unrelated settings. It also clears retained overrides for unavailable integrations, preserving unrelated settings.

## Integration boundaries

- **Membership and position integration:** resolve custom containers over defaults, persist committed topology and native coordinates through a defined recovery boundary.
- **Existing layout/session runtime:** apply effective placements, independent containers, packing, clipping, and availability consistently.
- **Native host and drag handle:** own hover targeting, pointer interaction, drag preview, cancellation, and commit requests.
- **Snap calculation and grouping resolver:** separate geometric candidates/guides from membership previews and commits; own no feature textures or readings.
- **Feature overlays/presentations:** continue supplying readings, measured sizes, visibility transitions, and drawing only.

The existing hover-label targeting already checks free-pointer state, drawable membership, and clipped bounds, and can supply the basis for handle targeting. Retain the host's selective input routing; simply calling `GuiDialog`'s default mouse methods would consume clicks over whole composer rectangles.

## Validation expectations

Start with a single draggable group prototype to establish whether the native titlebar can support hover-only rendering, selective input, cancellation, and persisted positions through the adapter. Verify that integration before extending it to individual containers and snapping. This prototype must not require changes to feature overlay or presentation classes.

Check coordinate conversion at multiple GUI scales; native saved-position round trips across client restarts; distinct group/indicator keys; reset behavior; resolution and style changes; group creation/insertion/removal and persistence recovery; consistent effective-anchor availability; snap tie-breaking and jitter; cancellation; and lifecycle cleanup. Position-only dragging must not refresh readings or recreate feature artwork.

In-game acceptance must cover free-cursor access, titlebar reachability at every screen edge, overlapping windows and focus, drag continuation outside bounds, no gameplay click-through during a drag, and ordinary input remaining unaffected away from eligible indicator bodies and handles. Source inspection establishes feasibility, not the final interaction quality.

### Snap feedback

Grouping snaps show a static reddish connection band over the shared attachment span, strongest beside the target item and fading into the incoming item. Alignment-only snaps retain thin reddish guides. Feedback follows the current preview and clears on release, cancellation, or Shift bypass.

Grouping acquisition measures the pointer distance to each finite target edge, independently of the incoming item size, origin, or grab offset. The closest edge selects the initial attachment side; a retained target/member/side remains preferred within the release threshold. Pointer position along that edge selects cross-axis alignment with the existing third-zone hysteresis. Incoming geometry determines placement and final viewport/overlap validation. This same rule applies at every screen edge. Alignment-only snapping remains based on the dragged bounds and total unsnapped displacement.

### Shared external attachments

Screen and native HUD alignment persist target/attachment/pivot/offset metadata on the same container model used by single indicators and groups. Shared anchor resolution uses the current measured footprint. Collapse/reappearance, native target changes, and GUI scaling retain this pivot. Destination attachments survive grouping/merging and override free outward-growth placement. Free or Shift-bypassed movement clears the moved attachment; cancellation restores it. Missing native targets fall back to the saved screen checkpoint and resume docking when available. Snapshot version 2 stores attachments and reads version 1 without rewriting it until an explicit save. Native HUD elements remain borrowed external anchors and never join the VE membership tree.
