# Installed inventory contract evidence

Revision note (2026-09-23): The direct-assignment and custom server-adapter recommendations below document the earlier design investigation. The user's later client-owned decision supersedes those recommendations. Installed API facts, including native `TryFlipItems` behavior and possible decoded client stack replacement, remain evidence for the revised [movement contract](ImplementationContract.md#client-owned-native-movement-contract). This historical fixture does not validate an atomic native multi-flip sequence.

Verified 2026-09-23 using PowerShell 7.6.6, .NET SDK 10.0.401, and the project's installed `G:/Vintagestory` assembly location. Both API and library report 1.22.7.0. See [raw results](installed-api-probe.txt) for SHA256 hashes, exact signatures, and installed IL call offsets; rerun with `pwsh -File docs/quick-tool/VerifyInstalledInventoryContract.ps1`.

## Evidence and limitations

The retained fixture passed against actual installed `ItemSlot` and `ItemStack` instances. It exercises rejected and stale-reference plans, complete A-to-B-to-A and A-to-B-to-C-to-A sessions, initially empty hands, a reference-preserving `[B,A,C] -> [C,B,A]` permutation, observers seeing only the complete permutation, and an exception during notification after commit. Eligibility booleans are controlled fixture inputs; this does not test production eligibility, a live server, backpack persistence, arbitrary mod callbacks, or network delivery ordering. No timing measurements or build/package runs were required for these documentation and investigation artifacts.

The installed nonvirtual `ItemSlot.Itemstack` setter is exactly `ldarg.0; ldarg.1; stfld; ret` (IL `02037D251200042A`): it assigns the reference without invoking callbacks. This supplies a narrow, synchronous commit boundary for a prevalidated permutation on the game thread. Capture the complete source reference array, validate every destination/restriction and current reference, then assign every final reference without any callbacks or await between assignments. Only after the full assignment sequence should notifications run. The guarantee is observer-level atomicity for this adapter on the game thread, not an engine transaction or crash durability.

A generic sequence of `TryFlipItems` is unsuitable. Adjacent `vsapi/Common/Inventory/InventoryBase.cs:398` calls local `TryFlipWith` before obtaining a packet. Installed `InventoryNetworkUtil.handleFlipItemstacksPacket` calls `InventoryBase.TryFlipItemStack`, then `NotifyPlayersItemstackMoved` or `RevertPlayerItemstackMove`. This accepts/rejects an individual engine flip; it does not establish a three-slot transaction. `PauseInventoryUpdates` controls incoming update queues and is not a transaction lock.

## Authority and notification boundary

Use a narrowly scoped server request/result adapter, with no client inventory prediction. Dispatch validation and commit to the server game thread (`IEventAPI.EnqueueMainThreadTask`), resolve locations from the authenticated player's own inventory manager, validate all sources and destinations, and preserve the server session's actual stack references. Client slot identifiers/revisions are advisory and must never authorize a stack supplied by the client. Serialize outstanding operations and deduplicate request identifiers.

Before commit, rejection/interruption leaves all slots unchanged. After commit, notification failures are **committed results needing reconciliation**, never an unchanged rejection. Catch/report individual notification failures, finish best-effort persistence/synchronization for every affected slot, and invalidate restoration if a callback has changed the resulting references. Arbitrary external callback mutations are not reversible by this adapter; silently applying snapshot rollback after callbacks could delete externally generated state. Implementation must distinguish committed, rejected, and committed-needs-reconciliation outcomes.

`ItemSlot.MarkDirty` calls `InventoryBase.DidModifyItemSlot` and transition processing; `DidModifyItemSlot` marks the slot dirty, calls inventory `OnItemSlotModified`, raises `SlotModified`, then calls collectible `OnModifiedInInventorySlot` (adjacent source lines 472 and 482 respectively). The installed `InventoryPlayerBackpacks.OnItemSlotModified` dispatches `ItemSlotBagContent` to `BagInventory.SaveSlotIntoBag`; bare `MarkSlotDirty` cannot substitute for that persistence. After all assignments, call each affected `slot.OnItemSlotModified(previousStackAtThisSlot)`: installed `TryFlipWith` passes the stack removed from that slot as the extracted-stack argument. This invokes persistence, inventory/collectible notifications, and transition processing. Do not treat the fixture's detached `MarkedDirty` callbacks as production notification code.

Installed `InventoryPlayerHotbar.NewSlot` creates `ItemSlotSkill` at index 10, `ItemSlotOffhand` at 11, and `ItemSlotSurvival` for ordinary slots. Determine eligibility from the supported runtime slot kind rather than including every index below `Count`. Eligible built-in inventory adapters must verify ordinary hotbar slots and backpack-content slots, including bag identity/topology, capacities, `CanHold`/`CanTake`, inventory access/locks, and both directions of every move. Bag equipment and unknown inventory implementations require explicit compatibility handling. Ordinary occupied target slots can participate in a full permutation; a blanket `CanTakeFrom` empty/merge check is unsuitable for validating a swap. Unknown virtual callbacks cannot be promised general rollback guarantees.


For explicit publication after notifications, use public `IServerPlayer.BroadcastPlayerData(true)` and `IPlayerInventoryManager.BroadcastHotbarSlot()`. Installed `ServerPlayer.BroadcastPlayerData` passes the boolean to `ServerMain.BroadcastPlayerData`, whose owner packet comes from `ServerWorldPlayerData.ToPacket`. The true branch enumerates `InventoryBasePlayer` inventories and serializes each through `InventoryNetworkUtil.ToPacket`; `ServerMain.SendPacket` sends that full state to the owner. The server hotbar manager calls `ServerMain.BroadcastHotbarSlot(player, true)`, publishing selected-slot/held-item appearance to other players. This is broader than a minimal dirty-slot packet but uses existing public operations and requires no hand-built vanilla packets. Queue/send the custom result after initiating native publication, while still verifying actual client receipt in later runtime work.

`InventoryNetworkUtil.SendInventoryContents(IPlayer,string)` and `SendDirtyInventoryContents(IPlayer,string,long)` are **protected virtual**, as recorded in the IL visibility output. Their call paths explain native synchronization but they are not callable public adapter entry points. Normal dirty-slot replication remains intact; explicit public full publication also supplies the reconciliation/status-refresh path. This investigation proves the available public call chain, not live delivery ordering or network acceptance.
## Item identity and reconciliation

The public `ItemStack` surface has class/id, stack size, attributes and temporary attributes, but no native immutable unique item identifier. Item code or equal attributes cannot distinguish duplicate tools. Installed `InventoryNetworkUtil.UpdateSlotStack` can assign a newly decoded stack, so client reference identity cannot survive synchronization.

Use server session reference identity while the session exists, exact expected locations and reference validation before each request, and invalidate if involved references are replaced or cannot be traced safely. Preserve reference identity through adapter permutations. Client snapshots serve rendering and stale-request checks only. Do not manufacture persistent item UUIDs or substitute another equal stack. A result acknowledges authority; ordinary inventory updates may arrive separately, so retain pending/reconciliation state until affected client contents match the authoritative result or a status refresh resolves it. Lost result/timeouts require status query, not replay of a movement under a new ID.


Installed `IServerEventAPI.AfterActiveSlotChanged` is `Action<IServerPlayer, ActiveSlotChangeEventArgs>`; `BeforeActiveSlotChanged` is `Func<IServerPlayer, ActiveSlotChangeEventArgs, EnumHandling>`. Subscribe to the after-change event to invalidate the server session immediately on manual active-slot changes, including switching away and back before another request. Combine this with eligible-inventory `SlotModified` notifications and the adapter's internal-operation guard; request-time hand comparison alone cannot detect that history. Installed lifetime hooks also include `PlayerDisconnect` and `PlayerRespawn` (`PlayerDelegate`) and `PlayerDeath` (`PlayerDeathDelegate`). Clear the corresponding server session at these lifetime boundaries and unsubscribe on system disposal. Exact signatures are retained in the raw log.
## Installed input and metadata findings

`GuiDialog` exposes `PrefersUngrabbedMouse`, `DisableMouseGrab`, `CaptureAllInputs`, and `CaptureRawMouse`; installed input/event members and tool methods are in the raw log. Tool classification uses `CollectibleObject.GetTool(ItemSlot)` rather than the raw `Tool` field. All 33 installed `EnumTool` names were recorded.

The public API has no directly verified game-window-focus property. The already referenced library exposes public static `Vintagestory.Client.ScreenManager.Platform` and public `ClientPlatformAbstract.IsFocused`. Installed Windows implementation reads `NativeWindow.IsFocused`. This enables a narrow version-specific focus adapter checked while the menu is active. `RegisterOnFocusChange` exists but appends to a delegate list without a verified unregister path, so avoid a permanent callback registration for this feature. Actual mouse/camera/focus behavior remains live-runtime verification.
