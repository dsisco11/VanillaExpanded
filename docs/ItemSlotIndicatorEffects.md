# Item-slot indicator effects

Effects attach to internal provider registrations. Providers still return `ItemSlotIndicator(Fill, Color)`; selection, priorities, and cached sampling remain independent of animation. Registrations without an effect use their selected ordinary presentation. This is an internal extension mechanism, not a public third-party API.

## Rendering styles

Actively spoiling perishables and meal contents use a purple indicator whose fill grows with the engine's perish transition progress toward rot. Before spoilage starts, the existing freshness fill and colors apply. Spoilage shares the freshness enablement, opacity, and selected rendering style; outlines show a purple border, while backgrounds and progress bars grow with spoilage. Meal-container food particles remain an independent quantity overlay. Items without a perish transition remain undecorated.

Freshness supports `SlotBackground` (the default bottom-up fill), `SlotOutline` (a complete border colored by freshness), and `HorizontalBar` (displayed as Progress Bar, a bottom track with left-to-right fill proportional to freshness). Select **Freshness Indicator Style** in ConfigLib, or set `PerishableItemFreshnessIndicatorStyle` in `VanillaExpanded.json` to `freshness-background`, `freshness-outline`, or `freshness-bar` respectively. Legacy numeric values 0, 1, and 2 also load. Invalid values fall back to the background. Selection does not resample freshness or restart shared simulations. Other providers retain their background presentation; meal-container food particles remain an independent overlay.

ConfigLib 1.10.12's initial JSON load leaves mapped dropdown keys at their defaults even when a different key is saved. The optional integration calls ConfigLib's public `TryReadFromFile` API for VanillaExpanded after its `ConfigsLoaded` event, restoring saved keys through its normal reload path before subsequent saves. During client startup, restoration waits for `LevelFinalize`: an earlier reload can broadcast through ConfigLib's disconnected network channel and abort between updating the value and its dropdown key. Both subscriptions are released on shutdown; restoration performs no file writes.

Registrations declare `defaultStyle`, `supportedStyles`, and an optional live `styleSelector`. The outline covers the slot perimeter using the inner half of the engine's 4.5-unit border stroke. Backgrounds and outlines reuse the prepared rectangle mesh and engine GUI shader. Bars use the engine's rounded-path and `ShadePath` helpers, strong dialog background, four-unit horizontal inset and two-unit height, and three-unit bottom margin. A bounded texture cache reuses unchanged sampled compositions and disposes entries on eviction or shutdown. Outlines draw after the inset item scissor is popped, preserving the enclosing dialog clip. Progress bars draw after the item inside its clip. Both disable depth testing inside the restoring GUI scope. Progress bars render fully opaque, including their track; the freshness intensity setting applies to backgrounds and outlines. All indicator settings are grouped under Item Slot Indicators in ConfigLib. Applicable zero-valued outlines and bar tracks remain visible, while zero-width bar fill is skipped. Absent providers and zero opacity remain hidden. Draw ranges and boundary cues apply only to backgrounds; bar length uses the actual resource fraction.

Effects declare `supportedStyles`, defaulting to background only. Unsupported, unavailable, or failed effects fall back to the selected ordinary style without changing provider selection. An effect with `drawBackground: true` draws the selected ordinary presentation beneath it only when the effect supports that style. Style support is part of immutable effect identity; it does not change shared program or mesh keys. Existing liquid, food, and crucible effects remain background-only.

## Registering an effect

Create one immutable definition and pass it to `ItemSlotIndicatorSystem.Register`:

```csharp
var effect = new ItemSlotIndicatorEffectDefinition(
    "vanillaexpanded:my-effect",
    Constants.ModId,
    "vanillaexpanded_itemslot_my_effect",
    segmentCount: 16,
    parameters: new Vector4(0.5f, 0, 0, 0),
    needsCameraMotion: true);
system.Register(provider, priority: -10, effect: effect);
```

Define and validate the units/ranges of the four parameter lanes in an effect-specific factory. Unused lanes should be zero. The generic definition rejects nonfinite parameters, unsupported ABI/topology, invalid names, and subdivision counts outside the geometry contract. Registration and GPU resource management belong on the client graphics thread.

IDs and asset domains use canonical lowercase names. Shader basenames must start with `vanillaexpanded_itemslot_`. Place the matching `.vsh` and `.fsh` files in `assets/<domain>/shaders/`. Reusing an identical effect ID/definition is allowed; conflicting definitions under one ID are rejected before changing provider selection. Appearance variants need distinct IDs, but may share the same shader domain/basename/ABI. The same engine shader name cannot identify conflicting program keys.

## Bounded draw levels

Providers may return `new ItemSlotIndicator(fill, color, new ItemSlotIndicatorDrawRange(0.2f, 0.8f))`. Omit the range for existing empty-to-full behavior. Levels are fractions of slot height/area measured upward from the bottom: mapped height is `minimum + resourceFill * (maximum - minimum)`. Thus resource fill 0 draws at 20%, 0.5 at 50%, and 1 at 80% in this example. The colored region remains bottom-anchored; the range limits its top edge, not its bottom. Use a positive minimum to retain visible fill at empty, and a maximum below one to retain headroom at full. Ranges require finite `0 <= minimum < maximum <= 1`.

Resource fill and color remain provider-owned samples. Only rendering maps fill. The shader receives mapped height as `fill`; resource fill and draw levels stay on the CPU for mapping and separate boundary-bar draws. The shader ABI remains unchanged. Effect deformation follows the common slot-containment and mapped-area contract below. Opacity zero remains intentionally invisible. Liquid containers and nonempty watering cans use the bounded range described below; other built-in providers retain their existing levels.

Within the nearest 15% of resource fill to an endpoint, one fixed horizontal bar marks that boundary. It fades in with smoothstep, reaches 60% of provider opacity at the endpoint, and uses RGB lightened 65% toward white. Its thickness is one pixel at a 48-pixel slot, scaling with slot size. The bar stays inside the slot and disappears in the middle range. The GUI rectangle path draws it after an effect returns to the GUI shader, or in the same scope as plain/fallback fill; no new shader assets or mesh uploads are needed. Cached range changes participate in adaptive activity detection.

## Geometry and shader inputs

ABI 1 uses indexed triangles and one `vec3` position attribute at location 0. Each vertex contains `(u, edge, 0)`: `u` is the normalized horizontal sample and `edge` is zero for the bottom or one for the surface. Quad topology requires one segment; fill strips accept 2–64 segments, with 16 as the default. Strip meshes have `2(N+1)` vertices and `6N` indices and are shared by ABI/topology/subdivision count. The built-in grain topology instead has 384 independent quads (1,536 vertices, 2,304 indices), with local corners in xy and grain identity in z; its shader supplies the same GUI depth 80.

| Uniform | Type | Meaning |
| --- | --- | --- |
| `projectionMatrix` | `mat4` | Current engine GUI projection |
| `modelViewMatrix` | `mat4` | Current engine GUI model-view, including dialog depth |
| `slotBounds` | `vec4` | Scaled pixel left/top/width/height |
| `fill` | `float` | Mapped geometry height in [0,1] |
| `color` | `vec4` | Sanitized straight RGBA in [0,1] |
| `timeSeconds` | `float` | Shared periodic animation clock in [0,64) |
| `motion` | `vec2` | Shared damped camera rates in [-1,1] |
| `cameraBob` | `float` | Shared damped local eye-height rate in [-1,1], positive upward |
| `effectParameters` | `vec4` | Immutable effect-specific values |
| `segmentCount` | `int` | Fixed mesh subdivision count |

Projection, model-view, bounds, and fill must remain active linked uniforms. Other common inputs may be optimized out; submission checks their presence. Preparation validates common uniform types and the single position attribute. Programs cannot use geometry stages, images, or UBOs. Built-in simulation drawing programs are the only sampler exceptions. The liquid program requires scalar `samplerBuffer liquidSurface`, integer `surfaceCellCount`, and integer `segmentCount`. Its shared surface buffer texture is bound on texture unit zero for the draw and released afterward. The food-grain program requires a sixteen-entry vec4 `foodPalette` array and scalar `samplerBuffer grainState`, likewise bound on unit zero and released after drawing. Other samplers remain rejected. Trusted shaders must also obey the output restrictions below; linked-input validation is not a shader sandbox.

For strip effects with a surface height `h(u) = fill + d(u)`, compute:

```glsl
vec2 position = vec2(slotBounds.x + u * slotBounds.z,
    slotBounds.y + slotBounds.w * (1.0 - edge * h));
gl_Position = projectionMatrix * modelViewMatrix * vec4(position, 80.0, 1.0);
```

For strip effects, keep horizontal coordinates, bottom anchoring, slot extent, and local depth unchanged. Require `abs(d) <= min(0.1, 0.25*fill, 0.25*(1-fill))` and zero discrete trapezoidal mean over the mesh samples. This preserves the represented area and forces zero deformation at empty/full fill. Prove the bound and mean analytically and sample every supported subdivision and boundary fill in tests. Clamping individual surface heights can bias area and is unsuitable as a substitute.

Strip fragment shaders write only attachment zero as `vec4(color.rgb * color.a, color.a)`. Grain drawing also premultiplies once, with stable tonal variation and elliptical-edge coverage multiplying the provider color and alpha. Premultiply once; retain provider opacity and color. Do not write fragment depth or introduce side effects. Default-mode zero fill or zero alpha skips drawing; bounded mode maps empty fill onto its minimum level and can still show a boundary cue; a provider's full-fill warning overlay remains full coverage even when the physical resource is empty.

## Animation, rendering, and ownership

An Ortho callback at order 0.99 publishes the frame snapshot before engine GUI dialogs render. It captures the resolved camera orientation and world eye position once, including the engine's view offsets and footstep bob. Independent liquid and grain simulations at order 0.995 consume that same camera sample and publish GPU state before dialog rendering at order one. Slot draws only read the snapshot and published surface. Time uses a monotonic clock and accepted positive intervals up to 0.25 seconds; long/invalid gaps contribute no catch-up. Shader time functions must be periodic over 64 seconds to avoid a discontinuity at wrap.

Camera capture occurs only when a registration requests it. Motion X represents looking right and Y looking up, normalized at four radians/second and damped with a 0.12-second time constant. Invalid/missing orientation, camera/player/world/mode replacement, inactivity, long gaps, or turns greater than pi/2 reset angular motion. Motion never invalidates provider samples.

The generic optional `cameraBob` uniform captures first-person local eye-height changes when `viewBobbing` is enabled, normalized at 0.5 blocks/second and damped with a 0.06-second time constant. World travel is excluded from this generic signal. Missing/nonfinite height, height jumps over 0.25 blocks, camera context changes, inactivity, and long gaps reset bob. The liquid simulation instead differentiates the resolved `MainCamera.CameraEyePos`, so translation, jumps, and rendered bob all contribute to its shared forces; it does not consume the generic `motion` or `cameraBob` uniforms.

The drawing resource owner prepares through the game's `IShaderProgram` factory, file registration, and compiler. Programs share domain/basename/ABI keys. Preparation happens at initialization, queued late-registration boundaries, and shader reload, never in a draw. Late registrations render plain until prepared. Reload invalidates old handles first, recompiles stable engine names, and retains successful fixed meshes. Failed mesh uploads may retry at reload. The liquid simulation owns its separate typed program and fixed state buffers. Shutdown unregisters both frame callbacks and shader events and disposes owned meshes/programs/buffers, tolerating engine disposal during reload; queued callbacks become harmless.

Rendering remains immediately before the original item call, inside its inherited clipping. Both paths disable depth writes while drawing, preserve inherited depth-test/cull state, and use engine premultiplied blending. They restore Standard blending, which the preceding slot-background helper establishes. Only three depth/cull state queries are needed. Rectangles use the GUI shader's `noTexture` branch and owned matrix scratch storage; they restore texture mode and model-view without changing engine matrix stacks or texture bindings. Effects switch through engine `Stop`/`Use` and return to the GUI program, whose engine-owned UBOs are rebound by `Use`. Subsequent item/overlay draws establish their own presentation and mesh/texture bindings. This contract is specific to the inspected slot-grid hook, not arbitrary renderer callers.

Missing or invalid resources select the rectangle using the winning provider's original fill/color. A draw failure disables only that effect until reload and restores state before fallback. Diagnostics are bounded per preparation attempt/effect, and host GUI failures are logged once per renderer lifetime. The original item call is still forwarded with all arguments; its exceptions are not swallowed. An unusable engine GUI shader cannot be repaired by indicator fallback.

## Adding and validating an effect

1. Add paired shader assets and a declaration factory with parameter validation.
2. Prove surface containment, bottom anchoring, mean area, empty/full behavior, and clock periodicity; add focused boundary tests.
3. Attach the definition to the intended registration without changing provider sampling or priority.
4. Inspect the built ZIP for both assets, then validate engine compilation/linking and appearance in a user-run client.
5. Test load failure, repeated shader reload, and shutdown in that graphics context; compare matched CPU/GPU workloads using the matched workload described below.

## Liquid sloshing

### Typed GPU simulation program

`Effects/LiquidSlosh/LiquidSloshSimulationShaderProgram` derives from the game's `ShaderProgram`. Its retained C# properties expose the solver's timestep, unified horizontal/vertical container acceleration, reference gravity, damping, cell count, and cell spacing. GPU inputs are a source buffer texture, destination buffer, dedicated transform-feedback object, and solver vertex array. The simulation owns those objects and must provide distinct source/destination storage with enough capacity; the shader class borrows them and does not allocate or dispose them.

The paired solver assets are `vanillaexpanded_itemslot_liquid_simulation.vsh` and `.fsh`, named by `LiquidSloshSimulationShaderProgram.ShaderName`. The vertex stage uses `gl_VertexID` to index cells, reads `samplerBuffer state` from texture unit zero, and emits two scalar floats named `nextHeight` and `nextFlow` per point. The other required uniforms are `timeStep`, `containerAcceleration`, `verticalShapeVariation`, `gravity`, `damping`, `wallDamping`, `wallDampingWidth`, `cellCount`, and `cellSpacing`. The caller supplies/registers these stages through the engine and calls `Compile()` normally. Geometry stages are rejected. The fragment stage supplies the engine's paired-stage contract and is unused during rasterizer-discard execution.

Source buffer textures use RG32F, with interleaved surface displacement/right-face-flow records, eight bytes each. Heights are signed deviations about a fixed reference depth of one, independent of individual item fill. Initialize heights with zero mean (zero everywhere for rest), and flows to zero. The last record's flow is the closed right-wall sentinel; the left wall is implicit zero. Each cell computes its two neighboring faces from the same immutable previous state, applying pressure slope, opposite horizontal camera acceleration, and exponential flow damping, then updates height from their flux difference. Interior fluxes cancel pairwise, conserving the sum of heights without clipping or a reduction. This is a linear shallow-water surface approximation, without nonlinear advection, wet/dry regions, or splashes. Flow damping uses exponential drag with a uniform baseline and additional drag near the walls, not spatial viscous diffusion between neighboring flows. Viscosity is not separately modeled or varied by liquid type. The displayed meniscus is an appearance term, not simulated surface tension.

Wall damping adds a smooth drag band over the outer 20% of each side. At face position `x`, its weight is `1 - smoothstep(0, wallDampingWidth, min(x, 1-x))`; the local flow decay is `exp(-(damping + wallDamping*weight)*timeStep)`. The owner uses base damping three and additional wall damping six per second, approaching nine at a wall while retaining three in the center. Wall strength must be finite and nonnegative; band width is a finite fraction in [0,0.5]. Zero strength or zero width disables the additional damping. Both cells adjacent to a face compute the same decay, so flux cancellation still conserves volume. The walls remain closed with zero boundary flow. This is an approximation for dissipating returning waves, not a perfectly nonreflecting boundary or explicit viscous diffusion. Hidden GPU checks verified shader/engine input validation, zero-strength/zero-width equivalence, symmetric edge weighting, and conservation. A right-going Gaussian packet returned peak amplitude 0.00091776 with wall damping versus 0.0015293 without it over 1.05-1.45 seconds (about 40% lower); summed-height drift stayed below 1.4e-9. The 986-case unit suite passed. This numerical test does not establish in-game appearance.

Wave propagation uses constant reference gravity, independent of camera acceleration. The former acceleration-dependent gravity could increase wave frequency twofold during a hard landing, despite correct fixed-step timing. Vertical acceleration now affects only the artistic broad-mode forcing term `-0.4*acceleration.y*S(x)`, which seeds vertical shaking even at rest. With shared variation `v` in [-1,1], `S(x) = 0.8*sin(2*pi*x) + 0.12*v*sin(pi*x) + (0.04 + 0.04*v)*sin(3*pi*x)`. The existing center/edge mode dominates; the two weaker broad modes vary side balance and shoulders. Absolute weights sum to at most one, all modes vanish at both walls, and identical face computations retain volume conservation. Hidden GPU checks at variation -1/0/+1 produced distinct forced profiles, retained rest without forcing, and conserved summed height within 8e-10. The dominant second-mode response was 0.00244190; the third mode reached at most 0.00035721 (14.6% of the dominant mode) in that test. The 995-case unit suite passed. The explicit solver requires `timeStep*sqrt(gravity)/cellSpacing <= 0.45`, checked by `Advance()` using managed inputs. The default step is 1/480 second. The owner performs enough fixed steps to represent accepted elapsed time, retains fractional time, and resets on discontinuities. Meniscus shaping and slot containment belong to the drawing stage, not per-cell height clipping in the volume-conserving solver.

Simulation compilation reuses engine stage compilation and diagnostics, then creates and links only its own OpenGL program through `SimulationShaderCompiler`. It declares feedback varyings before linking and caches active uniform locations from the final executable, including buffer samplers. The engine linker is never patched. Compilation failures release partial stage/program resources; retries create a fresh program instance. A dedicated feedback object requires OpenGL 4.0 or the corresponding transform-feedback extension.

The inspected engine's shader-source uniform parser recognizes 2D/cube samplers but omits `samplerBuffer`. Successful OpenGL linking therefore leaves `state` and `liquidSurface` absent from the engine's uniform-location dictionary, causing `HasUniform` and integer uniform submission to fail. Simulation programs discover all active uniforms directly after linking. For ordinary indicator rendering programs that still use engine compilation, `ItemSlotIndicatorBufferSampler` retrieves each actual linked sampler location and registers it in that dictionary before validation. All subsequent submission still uses the engine's `Uniform` methods. Missing/optimized-out samplers are rejected; this lookup occurs only at preparation/reload, with no per-frame GPU queries. The failure was reproduced against the installed engine parser after the client logs showed both effects falling back.

The simulation runs in a dedicated pass before GUI dialogs render, with no active feedback and rasterizer discard disabled on entry. Ortho order 0.99 is already inside the engine's GUI shader scope: the engine activates GUI before invoking the Ortho callbacks, not inside the GUI manager. Therefore the simulation owner retains the engine-managed current shader reference, stops it, activates the solver, and invokes `Advance()` for the required steps. In a finally block it stops the solver and re-uses the retained GUI program. This program handoff requires no GPU queries.

`Advance()` checks activation through engine-managed state, publishes retained inputs, binds its borrowed resources, and performs a fixed-count point update. It ends feedback even on draw failure, disables discard, releases feedback/VAO/buffer-texture bindings to zero, and leaves texture unit zero selected. It neither queries GPU state nor snapshots/restores arbitrary preceding bindings. Subsequent GUI mesh draws bind their own VAO/index buffers, and the buffer-texture scratch binding is separate from their 2D texture bindings. Execution performs no CPU readback.

`LiquidSloshSimulation` owns one 64-cell grid for the entire client. Two fixed buffers and their RG32F texture views alternate as source and destination; each completed step publishes the new source without copying or CPU readback. The owner uses spacing 1/64, timestep 1/480, gravity one, and damping three. The 1/480 timestep gives a Courant number of approximately 0.133 at reference gravity one. Camera impulses cannot change that propagation speed or stability bound. Hidden GPU mode crossings matched for vertical forcing 0/+3/-3 after subtracting forced-rest responses; vertical disturbance and conservation still passed. The 990-case unit suite passed. Allocation occurs once; shader reload retains those buffers, resets both states, and replaces the program. Disabling liquid indicators resets once and pauses advancement. Initialization or update failure publishes no surface, selecting ordinary indicator fallback until shader reload. The shared owner runs independently of how many slots are visible or drawn. The drawing strip remains sixteen segments; simulation resolution and displayed mesh subdivision are separate choices.

`Animation/ContainerMotionState` models a reusable conceptual container point at camera-local offset `(0, -0.2, -0.8)` blocks: slightly below and ahead of the eye. Its position delta is the camera's world position delta plus the change in that offset transformed by the camera basis. This converts rotation into actual displacement at a lever arm, including pitch and roll, rather than adding angular rates to linear acceleration with separate artistic weights. Differencing the offset trajectory includes tangential and centripetal effects implicitly. Camera origin positions are subtracted in double precision before converting their small differences to floats, preserving motion far from the world origin.

The combined point velocity is filtered with a 0.025-second time constant. Differentiating that history produces world acceleration, filtered with a 0.045-second time constant. Both histories remain in world coordinates so changes to view axes do not manufacture acceleration. The generic state publishes filtered `WorldVelocity`, `WorldAcceleration`, `LocalVelocity`, and `LocalAcceleration` vectors in physical units, retaining all three axes. It has no liquid, GPU, noise, or solver dependencies. `LiquidSloshMotionState` composes this state, selects right/up acceleration, and applies one conversion gain of 0.2 solver units per block/second squared. A uniform magnitude limit of three retains direction. Motion reaches the solver through the unified `ContainerAcceleration` property / `vec2 containerAcceleration` uniform; no separate bob, translation, rotation, or history uniforms are needed. Starts, stops, and direction changes arise from the velocity difference; constant straight-line movement settles. The GPU height/flow state supplies longer-lived liquid inertia after the forcing stops. The one-dimensional solver cannot represent independent forward/backward surface waves; that acceleration component is excluded instead of being arbitrarily mixed into vertical forcing. Gravity remains the solver's scalar reference rather than a full orientation-dependent gravity model.

Camera/world/player/mode changes, invalid pose, movement greater than two blocks in one sample, turns greater than pi/2, and elapsed gaps greater than 0.25 seconds establish a neutral baseline and reset the grid. The first valid velocity sample creates no artificial impulse. No accumulated time is replayed across a discontinuity.

Vertical movement also creates a small artistic lateral jostle: after projecting container acceleration, add `0.08 * abs(verticalAcceleration) * smoothNoise` to the lateral component, then apply the existing magnitude limit. The noise uses deterministic signed hash values at 0.35-second intervals and quintic interpolation, giving continuous first/second derivatives at knot boundaries. Its clock advances by accepted elapsed time rather than frame count, is shared by the single motion owner, and resets with camera discontinuities. It never enters velocity or acceleration history and supplies the shared `verticalShapeVariation` scalar uniform for the vertical-force blend. The lateral perturbation amplitude follows the filtered vertical acceleration and settles to zero with it, so a still container acquires no idle forcing. Shape variation also multiplies vertical forcing and cannot disturb a stationary grid by itself. This represents imperfect handling; it is not fluid turbulence and does not remove the solver's standing modes.

Turning response is primarily transient. At a stationary camera origin, steady yaw produces mostly forward/backward centripetal acceleration at the conceptual point, which the right/up solver projection excludes. With the earlier 0.4-block forward offset, a 120-FPS motion-state check ramping yaw to one radian/second over 0.2 seconds measured lateral solver acceleration that peaked at 0.3895 during startup, settled to 0.005623 during steady turning, and peaked at 0.8538 on an abrupt stop. These are CPU forcing measurements, not visible surface amplitudes. The model tracks one offset point rather than distributed rotational forces across the fluid. Its short lever arm, velocity/acceleration filters, and solver damping further soften brief motion. The forward offset is now doubled to 0.8 blocks to strengthen turning transients while retaining the unified acceleration input; it does not introduce continuous turn-rate forcing. Repeating that trajectory produced startup/steady/stop forces of 0.77898/0.011246/1.70766, twice the previous values. The 986-case unit suite passed with the new offset.

The 64-cell grid and 1/480-second step passed standalone GPU solver checks and actual buffer reset/disposal checks; the associated unit suite passed 986 cases. These checks retain the live appearance and performance limitations described below.

On 2026-10-04, the solver stages compiled/linked and executed through transform feedback in a standalone hidden OpenGL 3.3 context on an RTX 4090 / NVIDIA 591.86, without launching the game. With 32 cells, spacing 1/32, timestep 1/240, and gravity one, checks covered zero rest, opposite acceleration response, closed-wall flow, braking reversal, vertical disturbance, conservation, and damping. Thirty forced steps retained zero summed displacement; a vertical impulse had summed-displacement error 3.87e-12. Damping over 2,400 steps reduced the tested energy measure to 2.42e-9 of its starting value. Actual managed buffer checks verified alternating publication, zero reset of both GPU states, and double disposal with no owned handles remaining. The attributed Harmony patch installed during its scoped callback and was removed on both success and exception. These checks do not establish in-game appearance or performance. The published package includes both solver and drawing asset pairs.


### Shared granular food effect

`FoodGrainSimulation` advances a single normalized, closed 2D container before GUI dialogs, independently of slot draws. Its engine `ShaderProgram` subclass exposes typed inputs and uses the shared simulation compiler to declare feedback outputs before linking its own program. Startup and shader reload validate uniforms and two ordered vec4 feedback outputs. Each grain stores position/velocity and previous-position/radius/reference-height in two RGBA32F buffer texels. Two buffers alternate after every dependent pass; drawing reads the completed state without CPU readback.

The first implementation limits catch-up to eight substeps per frame, dropping excess elapsed time to avoid a work spiral. It uses 384 circular collision particles, deterministic irregular rejection-sampled positions, broadly varied radii from 0.010 to 0.023, gravity four, and fixed 1/120-second steps. Each step predicts motion, executes eight relaxed Jacobi contact passes, and reconstructs velocity. Contact passes scan all other particles, separate overlapping equal-mass circles, constrain closed walls, and resist relative tangential displacement with static/dynamic friction. Each invocation updates only its own grain. Velocity drag of 0.65 per second, inelastic walls, bounded acceleration, and a speed limit discourage unstable impact responses. Contact relaxation remains 0.65 with eight iterations; a trial increase to 0.75 increased jitter and penetration rather than making the dense bed firmer. Generic container acceleration is projected onto right/up, with downward acceleration omitted so falls cannot cancel gravity or launch grains. Upward braking and landing still apply compressive force. The remaining vector is scaled by 0.30 and direction-preservingly limited to six particle units. No idle force is applied.

Food colors come from ingredient `Collectible.GetRandomColor(client, ingredientStack)`, the same particle-color API that respects item particle texture selection and is used by meal color sampling. Sampling ingredients directly avoids ceramic colors from storage vessels such as crocks. Sixteen RGB samples are cached weakly per container stack and reused until client or ingredient collectible identities change, so refresh timers do not flicker grain colors. Packed engine RGB channels are decoded without carrying atlas alpha; the indicator controls grain opacity. A stable hash chooses each grain's palette entry independently of motion, and palette uploads use engine `Uniforms4` without per-draw allocation. This is a sampled palette, not an exhaustive list of texture pixels. Custom palettes changing solely through ingredient attributes or an atlas reload retain their cached samples until the stack/client/ingredient identities change.

The independently selected freshness rectangle is drawn and restored before food-amount particles blend over it. Other effects can still opt into background drawing on their definition and retains existing depth masking and clipping; failed particle submission does not draw the background twice. The effect owns fixed quad geometry: xy encodes grain corners and z encodes particle identity. The vertex shader reads shared state, varies visual orientation and palette index by a stable hash of particle identity, and maps grain centers into the food-amount range while retaining grain dimensions. Visual grain radius is the greater of three times collision radius and 0.05 slot units, keeping the smallest pieces large enough to show corners at inventory-slot scale, with a stable per-piece aspect ratio from 0.55 to 0.9. Four or five active random Voronoi bisectors define angular food silhouettes, using the same half-plane construction as solid crucible pieces but fewer sides and more varied offsets. The remaining lanes in the six-plane interface are inactive. Longer edges and stronger corners avoid near-regular hexagons reading as circles at inventory-slot scale. Bisectors are prepared in the vertex shader; fragments intersect their half-planes and use a one-pixel linear coverage ramp rather than a wider smoothing band that softened small corners. Center mapping accounts for the enlarged rotated quad extents at the floor, surface, and walls; collision simulation is unchanged. Ingredient palette selection remains unchanged. A raised-center surface follows the cell planes: the largest normalized half-plane coordinate selects its local facet slope, including the quad clipping planes. The inverse aspect scale and particle rotation transform that slope into slot-space normals. Food uses softer matte shading with a rounded-center normal transition; metal uses sharper planar slopes and a restrained specular highlight. Both use a shared upper-right light in slot right/up coordinates. Food RGB is additionally lit by the current height gradient from 40% at the floor to 95% at the nominal pile surface. Height is normalized by the displayed fill so lower contents retain the same lighting range. Opacity is unchanged. A particle-opacity gain of 0.95/0.35 gives 0.95 interior alpha at the default freshness intensity of 0.35, while lower intensity still reduces particle opacity. The fragment treatment clips to the slot; existing depth masking and boundary bars remain in the common renderer. Velocity finalization publishes a fixed resting envelope from total collision-circle area divided by a calibrated packing fraction of 0.78 for food, or 0.675 for metal. Drawing maps centers against this constant reference rather than the instantaneous tallest particle, avoiding collective visual compression and expansion. Individual food excursions are contained by the 0.85 upper draw level using rotated quad extents, without rescaling other pieces. These packing fractions estimate presentation height; soft circle contacts remain approximate. Drawing selects a stable prefix of ceil(384 * resourceFill) food particles, or ceil(128 * resourceFill) solid-metal pieces, before reading particle state. Zero contents select zero particles; any positive amount selects at least one. This uses the original contents fraction rather than the bounded draw height, so half contents display half the particles even when the minimum draw level is nonzero. Random initial placement makes the identity prefix spatially irregular; retained particles keep their sizes, rotations, shapes, and palette entries. Center mapping still places the selected particles within the requested draw height, but fewer particles now occupy a smaller pile. Visual overlap remains possible because enlarged visual silhouettes exceed collision radii. Shared simulations continue to model the full reference pile, including hidden particles, so this is a per-slot quantity presentation rather than a separate physical simulation at each contents amount. Drawing different amounts does not reset, resize, or advance simulation buffers. The circle envelope reaches the requested height, while the clipped cellular silhouette can fall slightly below it. Collision shapes are circles, visual orientations are fixed, and this model has no 3D grains, angular collision dynamics, cohesion, or spatial neighbor acceleration. Shader failure selects the existing rectangular fallback until reload. GPU numerical receipts and user-run appearance are separate acceptance boundaries.

### Current surface effect

Food containers combine the selected freshness presentation from FreshnessIndicatorProvider with a particle-only food-amount overlay from FoodContainerIndicatorProvider. Vessel classification requires meal handling plus mealContainer/eatenBlock/emptiedBlockCode metadata; pies retain only ordinary freshness. Serving count divided by capacity controls both particle count and height independently of food age.

Liquid containers and watering cans share `LiquidSloshIndicatorEffect.Definition`, a sixteen-segment vertex effect enabled with their existing indicator setting. Normal liquid samples use average surface levels 0.15–0.85, preserving raw resource fill, color, opacity, sampling, and priority. Empty dedicated liquid containers retain a small blue liquid surface and the minimum boundary cue. Food-capable vessels marked by the game's `mealContainer` attribute, such as bowls, show a liquid indicator only when they contain a positive liquid volume; empty bowls show none. Empty watering cans instead retain their existing unbounded full red warning: mapped fill is one, deformation is zero, and no boundary cue is drawn. Other providers remain ordinary rectangles.

With `u` measured left to right, the drawing shader linearly interpolates adjacent cell-centered heights from the shared GPU buffer, extending the nearest cell at each wall. Simulation displacement has gain five. The artificial idle standing wave has been removed, and the liquid drawing shader no longer consumes `timeSeconds`. A settled simulation displays a static meniscus; all surface motion comes from the evolving fluid state.

Remaining regular wave patterns arise from the linear homogeneous grid's reflections from two closed walls. Vertical forcing now blends three broad modes, with weak side/shoulder weights driven by the existing shared smooth noise. Uniform horizontal forcing and symmetric geometry repeatedly excite similar standing modes; nonlinear flow/advection and turbulence are absent. An even cell count is not the cause of these repeating shapes. All moving surface terms now respond to simulation damping. The active solver damping is three per second, increased from two.

A permanent meniscus adds `0.1875 * ((2*u - 1)^4 - m) / (1 - m)`, raising the outer edges with a shallow depression in the middle. For `N` strip segments, `m = 1/5 + 4/(3*N^2) - 8/(15*N^4)` is the exact discrete trapezoidal mean of the quartic shape. The existing `segmentCount` uniform supplies `N`. Parameter lanes encode simulation gain divided by eight, two reserved zero lanes, and meniscus weight.

Cell centers and mesh vertices sample different grids. The shader computes the combined profile's discrete trapezoidal mean and maximum absolute sample value over the actual `N+1` surface vertices. It subtracts that mean, then scales uniformly by `1/max(1, peak + abs(mean))`. Since `abs(value - mean) <= peak + abs(mean)`, the normalized profile is bounded by one and retains zero sampled mean. Multiplication by `a = min(0.1, 0.25*fill, 0.25*(1-fill))` preserves represented fill area and slot containment without clipping individual heights. Empty/full warning overlays remain flat. Limits mark average height; the separate boundary bars stay fixed. Bottom anchoring, depth, provider color, and simple premultiplied fragment output are unchanged.

## Independent freshness and food amount

FreshnessIndicatorProvider again includes meal containers, preserving direct perish states and the inventory-rate-aware content fallback. It selects the ordinary colored background. FoodContainerIndicatorProvider independently selects a particle-only overlay for actual vessels, with fill equal to quantityServings / servingCapacity (default capacity one), clamped to [0,1]. Empty or invalid serving amounts produce no particles; perishable state is not required for food amount. The grain definition no longer requests a colored background. Its bounded 0.20–0.85 range and boundary cues now represent food amount rather than freshness. Both currently retain the existing freshness feature setting and intensity.

Provider registration has an explicit overlay flag. Primary and overlay providers have independent priority selection and caches, allowing freshness and food amount to coexist without allowing lower-priority ordinary providers to draw indiscriminately. Overlay-only results remain renderable. Food amount uses adaptive sampling. Rendering restores each layer before the next, and each layer has independent failure/fallback behavior. Ingredient palettes and the shared grain simulation remain unchanged.

Effect enablement: EnableLiquidSloshEffect and EnableFoodGrainEffect default to true and are exposed through ConfigLib and the JSON configuration. Changes apply immediately. Disabling liquid slosh selects plain volume fills without changing provider samples; disabling food grains hides the food-amount overlay while freshness remains available. Each disabled simulation resets once and stops updating. Prepared resources are retained for immediate re-enablement. Food and solid-metal granular state now have independent enablement and ownership.

## Crucible metal amount

[CrucibleIndicatorProvider](../VanillaExpanded/src/CrucibleIndicators/CrucibleIndicatorProvider.cs) selects solid and molten presentations through two registrations. Filled `BlockSmeltedContainer` stacks use `GetContents` for metal units and output identity, and `HasSolidifed` for the game's pouring threshold (90% of the contained metal's melting point). Container temperature supplies heat tint independently of quantity. Empty and unresolved contents are excluded. The ceramic crucible's melting point is never used to classify its metal.

A fired `BlockSmeltingContainer` only has ingredient contents while it occupies input slot one of `InventorySmelting`. The provider reads the cooking slots through the block API, uses the game's matching alloy or single-metal conversion, and rounds output quantity to metal units as the smelting operation does. It remains a solid-piece presentation until the game produces the smelted-container stack. An empty fired crucible in a backpack has no indicator; the separate firepit ingredient slots are not treated as crucibles.

The game exposes no fixed metal-unit capacity for this container. `CrucibleIndicatorCapacityUnits` is therefore an adjustable visual full-level reference, default 2,560 units (four 128-item stacks of five-unit nuggets), rather than an enforced storage limit. Amount is clamped to this reference and mapped to the existing 0.15–0.85 draw range with separate fading boundary bars. `EnableCrucibleIndicators` hides the whole presentation; `EnableCrucibleEffect` retains plain quantity fills. Both settings and the reference apply live through ConfigLib or JSON.

Solid metal uses angular, randomly oriented faceted pieces above a continuous metal-colored fill. After the shared food state looked too freely flowing in the user's live test, metal now owns an independent 128-chunk simulation. It reuses the existing granular scheduling, typed engine ShaderProgram, and ping-pong storage implementation, with separate engine registration, buffers, reload, reset, and disposal. All solid crucible slots share that one completed metal state; slot rendering never advances it. The cached 384-quad mesh remains reusable: one in three quads reads compact metal particle index i/3. Food continues to read its own 384-particle state unchanged.

Metal collision radii are 0.018–0.035 versus food's 0.010–0.023. The metal shader uses gravity 6, drag 5 per second, speed limit 1.2, static contact friction 0.55, dynamic contact friction 0.4, and wall friction 0.55. Camera forcing uses horizontal gain 0.6 and vertical gain 0.75, capped at combined magnitude 6, while food uses gain 0.30 on both axes capped at 6. Strong drag and gravity give metal its heavy settling response; contact friction now allows ordinary camera impulses to shift the pile. Both exclude downward acceleration from vertical forcing, avoiding persistent lifting during falls. Metal retains fixed 1/120-second steps with eight contact iterations and bounded catch-up. The smaller independent count limits the additional quadratic contact workload. This remains a soft circular-contact model with angular visual pieces and fixed random orientations, rather than polygonal rigid-body rotation or a simulation of the actual cooled solidified slug.

The former horizontal gain 0.12, force cap 2.5, and contact friction 1.2/0.9 suppressed average movement below one pixel in realistic camera-path checks, matching the user's report that the bits appeared stationary.
